# 答辩演示脚本（约 8—10 分钟）

> 打开浏览器访问 `http://127.0.0.1:5050`（按启动时打印的地址为准）。
> 建议提前执行 `python tools/init_db.py` 恢复一份干净演示数据。
> 演示账号密码均为 `123456`。

---

## 0. 开场（20 秒）

> "本系统按报告的设计实现了中网赛事运营管理系统的五个模块：系统管理、基础数据、赛程编排、成绩管理、公开查询。
> 技术栈是 Python Flask + MySQL，B/S 三层架构，数据库按报告的 6 张主表设计，另外按非功能需求加了操作日志表。"

先停在**观众端首页**（未登录状态），说明："观众不需要登录，直接看赛程。"

- 指向页面顶部："这是观众端，只有查询，没有任何编辑入口。"
- 切换到"选手资料"页，点一位选手，展示胜率与参赛记录。

## 1. 工作台与角色权限（1 分钟）

点"工作人员登录" → 用 **admin01 / 123456** 登录。

> "登录后进入工作台，三个提示条对应报告 4.6 节：当日比赛场次、待处理冲突数、待录比分场次。"

- 指出"待处理冲突数 = 3"："数据里故意留了两组时间重叠的赛程，系统能扫出来，这正是编排模块要解决的问题。"
- 展示左侧菜单："管理员能看到全部模块。"
- **权限演示**：右上角退出，用 **record01 / 123456**（成绩录入员）登录 → 左侧菜单只剩「工作台、成绩管理、观众查询端」，直接在地址栏输入 `/schedule/` → 显示 **403 无权访问**。
  > "报告 4.7 节要求菜单级 + 页面级双重控制，直接输网址也绕不过去。"

## 2. 基础数据管理（1 分钟）

用 **schedule01 / 123456**（赛事编排员）登录 → 基础数据管理 → 运动员档案。

- 用国籍 + 性别 + 排名区间检索一次。
- 点"新增运动员"填一个名字保存（弹窗表单），列表出现新记录。
- 试删一个仍有未结束比赛的运动员（例如 王梓轩）→ 被拒绝并列出关联比赛编号（FR-03）。
- 场馆档案页：把某片场地改为"维护中"，弹窗提示"该场地已有 N 场比赛需要改场"。

## 3. 赛程编排 + 冲突校验（核心，2—3 分钟）

进入"赛程编排"。

1. 先演示**正常编排**：项目选"男子单打"、轮次"首轮"、日期选 2026-09-28、时间 16:00、场地选一个可用场地、裁判选一名可排裁判、双方各选 1 名男选手 → 保存成功，当日赛程表立即出现该场。
   > "这对应测试用例 TC-01。"
2. 再演示**冲突拦截**：在已有比赛的时段（如 2026-09-28 13:00 钻石球场）再排一场。
   - 保存后：顶部红字提示"检测到 2 项冲突，比赛未保存"；
   - 表单内容**完整保留**（不用重填）；
   - 表单下方逐条列出"场地时段冲突 / 裁判执裁冲突"，每条都标注冲突的比赛编号 M260005，可点击跳转；
   - 同时给出"候选空闲场地"和"候选空闲裁判"。
   > "报告表 4 的异常流程要求指出具体冲突对象、返回修改，这里做到了；校验顺序是先选手、再场地、后裁判。"
3. 说明**边界规则**：一场 11:00 结束、下一场 11:00 开始 → 允许保存（TC-04，"首尾相接不算冲突"）。
4. 到"赛程表"页：按日期/场地/项目筛选，点"导出 CSV"下载，打开展示中文表头正常。

## 4. 成绩录入与统计（1.5 分钟）

退出，用 **record01 / 123456** 登录 → 成绩管理 → 成绩录入。

1. 左侧选一场"进行中"的比赛（如 M260018），右侧录入盘分 `2:1`、局分明细 `6:4 3:6 7:5`、实际时长 `95` → 保存成功。
2. 页面提示成绩已锁定；再对这场录一次 → 被拒绝（TC-05）。
3. 故意输入盘分 `3:0`、局分带字母 → 表单标红提示（TC-06）。
4. 打开"统计报表"：已结束场次、平均时长、按项目/场地/性别分布、胜率榜都随之变化。
   > "保存比分时，写比分、置状态、给双方累加胜负场次这三步在同一个数据库事务里，任何一步失败整体回滚，避免报告 4.3 节说的'比分写了胜负没更新'。"
5. 点"导出统计 CSV"。

## 5. 观众端同步（30 秒）

换一个新标签页（或退出登录）打开 `/public/`，选到刚录分的日期：

> "比分录入后观众端立刻能看到，赛程和成绩是同一份数据，不需要人工誊抄发布。这就是报告里'一次录入、多处复用'的目标流程。"

## 6. 系统管理与收尾（1 分钟）

用 **admin01** 登录 → 系统管理：

- 账号管理：新增一个账号、改角色、重置密码、停用（演示停用后该账号无法登录）。
- 操作日志：能看到刚才所有新增/修改/删除/状态变更/录分/登录的记录，带操作人和时间。

收尾（可讲三点技术要点）：

1. **冲突校验**：时间换算成分钟区间，`a1 < b2 and b1 < a2` 判重叠，天然满足"首尾相接不算冲突"；
2. **事务一致性**：成绩录入三步用 `db.transaction()` 绑成原子操作；
3. **权限**：菜单级、页面级、操作级三层，配合加盐哈希、登录锁定、会话超时与操作日志。

> "另外按报告 5.3 节写了 49 项端到端自动化测试，`python tests/test_e2e.py` 可以一次跑完 TC-01 到 TC-08。"

## 常见提问与回答要点

| 问题 | 回答要点 |
| --- | --- |
| 为什么用 MySQL 不是 SQLite？ | 课程要求 Python + MySQL；表结构、主外键、唯一键、CHECK 约束完全按报告 4.5 节平移，单文件备份优势在 MySQL 用 mysqldump 实现。 |
| 冲突校验怎么保证不漏？ | 保存前在后端做，不依赖前端；同一场地的时段占用还有 `(court_id, match_date, start_time)` 唯一键兜底。 |
| 双打怎么处理？ | 参赛表 `match_player` 是 m:n 关联表，一场比赛 2 或 4 条记录，`team_no` 区分双方；胜负场次按队伍给每名选手累加。 |
| 成绩录错了怎么办？ | 按 BR-04 成绩锁定，录入后不允许重复录入；本期未开放「管理员更正成绩」入口，如需更正只能在后台数据库层面处理（属报告 6.2 节列的不足）。 |
| 数据量大了怎么办？ | 一届赛事约 500 场比赛、300 名运动员，MySQL 索引（日期、场地、裁判、选手）足够；后续可把编排扩展为批量自动生成（报告 5.4 节）。 |
